我们为什么用 Rust 重写同步引擎

作者：Mira Hassan · 2026 年 4 月 22 日 · 8 分钟阅读

两年来，我们的 Go 同步引擎一直够用。直到视频剪辑师开始加入客户名单，我们一直礼貌性忽略的 GC 停顿，变成了无法再忽视的 bug 报告。

这个决定并非突然。我们观察 GC 停顿分布的变化已有六个月，才承认数据在告诉我们什么。P50 延迟表现优异，P99 却像一部恐怖片。那些在活跃编辑会话中同步 30 GB .psd 文件的客户，正是最先来反馈的人。

重写整个同步引擎，听起来就像那种所有人都告诫初创公司千万别碰的项目。我们还是做了。以下是过程、令我们意外的部分，以及我会做出不同选择的地方。

导火索：无法修复的 GC 停顿

Go 的垃圾回收器很出色，但本质上也是一种取舍。我们的热路径在每次块差异计算时都会分配短命的缓冲区切片——在大量上传的规模下，回收器运行得足够频繁，P99 停顿悄悄超过了 50ms。

我们尝试了常规方案：用 sync.Pool 池化缓冲区、调优 GOGC、减少合并路径中的分配。每项都有点帮助，但没有一项能把延迟压到 20ms 以下，而我们在意的客户需要的是 5ms 以下。

“我们无法在 Go 中修复它，但可以用一种没有 GC 的语言来修复。”

我们的高级工程师 Sasha 在十月的会议上说了这句话。他说得对。问题不在于要不要离开 Go，而在于用什么替代它，以及我们能保留多少。

保留了什么，舍弃了什么

CLI 留在 Go，控制平面也留在 Go。而那个在客户笔记本热循环中做块级差异计算的模块，改成了 Rust。边界收敛为单一的 FFI 接口，配上一个精简而强约定的协议。

以上数字真实来自生产环境，但脱离上下文也有误导性：Rust 移植版不只是去掉了 GC，还去掉了一层我们从 Go MVP 时期就一直背着的抽象。

如果重来，我会怎么做

只有一点：FFI 边界。当初为了对称性，我们选了 cgo——当你的代码库里到处都是 Go 时，让 Go 调用 Rust 感觉很自然。但绑定过程很脆弱，在写出一次性处理这些问题的包装层之前，字符串生命周期错误让我们吃了两次生产事故。

如果今天重新开始，我会选择 uniffi，或根据 schema 生成绑定。教训不是别用 cgo，而是一旦跨越语言体系，就把边界当作外部 API 来对待。
